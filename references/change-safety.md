# 改动安全：防止改一处坏一处

对应问题：修一个对齐问题导致别的页面错位；越修越乱；样式互相打架；声称已修复但没验证。

## 1. 改动范围

- 只改与任务直接相关的元素。发现无关问题时记录下来在汇报中提出，不顺手改。
- **不修改**以下内容，除非任务就是改它们：全局样式文件（reset、base、global.css）、共享组件、主题/令牌、Tailwind 配置、通用工具类（`.flex-container` 之类）。
- 必须改共享内容时：先 grep 它的所有使用处，列出受影响的页面，改后对这些页面也跑 layout_check。
- 局部需要不同样式时，用组件的 variant/props 或组件局部的 class，不去改全局类的定义。

## 2. 禁止的修补手法

这些手法能让眼前的问题消失，但会制造更难查的问题：

| 禁止 | 原因 | 应该 |
|---|---|---|
| `!important` | 破坏层叠顺序，下一次只能用更多 !important 压 | 找到冲突的规则，修正来源 |
| 提高选择器权重（`.a.a`、嵌套 id） | 同上 | 同上 |
| 负 margin 拉回位置 | 掩盖了真正的间距/布局错误 | 修正父级布局或 gap |
| 魔法数字（`top: 37px`、`height: 413px`） | 内容一变就错 | 用文档流 + 弹性尺寸 |
| 随手加大 z-index | 引发层级军备竞赛 | 见 layering.md，用层级令牌 |
| `overflow: hidden` 藏住溢出 | 同时裁掉浮层和真实内容 | 修正溢出的根因（通常是 min-width） |
| 针对单个断点打补丁覆盖 | 其他宽度仍然坏 | 用不依赖断点的弹性写法 |
| Tailwind 同一属性写两个类（`p-4 p-6`、`flex block`） | 结果取决于 CSS 生成顺序，不可预测 | 每个属性只保留一个类（响应式/状态前缀除外） |

## 3. 回归流程

1. 改之前：对目标页面（以及共享改动的受影响页面）运行 `layout_check.cjs --out .ui-guard/before`。
2. 改之后：运行 `layout_check.cjs --out .ui-guard/after`。
3. 对比两份 report.md 的问题数量和截图。新增的问题必须处理。

## 4. 验证与汇报纪律

- 不能验证的，不说"已修复"，说"已修改，未能渲染验证，请在 X 宽度下确认 Y"。
- 汇报修复时附上证据：检查项、宽度、修复前后问题数、看过的截图。
- 用户报告"还是不对"时，先重新渲染并看截图确认现状，不要基于记忆中的代码直接再改。
- 同一个问题连续修了 3 轮仍未解决，停下来：描述观察到的现象、已尝试的方案、怀疑的根因，请用户提供截图或确认预期。
